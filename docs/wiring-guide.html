How TenantPilot is wired

TenantPilot onboards a customer, connects their systems, runs a governed AI agent against them and ships the whole thing to Kubernetes. This page shows the machinery: one question traced through the system, the walls between tenants, the gates on every tool call, the context budget, and the path from commit to cluster.

One question, end to end

“Customer C-104 says their installation failed. What happened and what should we do?” Sixteen hops later, the operator gets an answer where every claim cites its source. Point at a phase below to light up its hops.

hops 1–3

Authenticate and scope

The JWT says who you are; membership says which tenants you may touch, and anyone else gets a 403. A Redis counter caps each tenant at 30 runs a minute across every API replica. Then every query runs in a transaction scoped to Acme:

SELECT set_config('app.current_tenant', :tid, true)
-- true = transaction-local: gone at COMMIT, so a
-- pooled connection never carries it to the next request
hops 4–5

Discover tools

The runtime asks the MCP server what exists instead of hard-coding tools, then keeps only what Acme enabled. create_ticket advertises readOnlyHint: false, so it arrives pre-marked as approval-gated. New tools show up here automatically but start disabled for every tenant.

hops 6–7

Retrieve and budget context

Up to 12 candidate chunks come back from the tenant's HNSW index. The ContextBuilder drops weak and duplicate ones, ranks the rest and fills a 3,362-token knowledge budget. Each survivor becomes K1, K2… with a logged reason.

hops 8–9

Let the model choose

The model sees only enabled tools and answers with a structured call, never free text the runtime has to guess at:

{"type": "tool_use", "name": "get_customer",
 "input": {"customer_id": "C-104"}}
hop 10

Govern the call

Code decides, not the prompt. Permissions are re-read every turn and arguments are checked against the tool's JSON Schema, so "priority": "URGENTTT" is rejected before any network call. Write tools stop here and wait for a human.

hops 11–15

Execute through MCP

A 5-minute service token pins the tenant and the allowed tools, and the MCP server rejects anything else. The connector decrypts Acme's key, calls its API (retrying 5xx, at most 3 attempts), maps customer_ref → customer_id and returns source T1.

{"aud": "tenantpilot-mcp", "scope": "mcp:tools",
 "tenant_id": "<acme uuid>", "run_id": "…",
 "allowed_tools": ["get_customer", "list_open_jobs", …],
 "exp": "issued + 5 min"}
hop 16

Answer with evidence

After list_open_jobs (T2) and the runbook excerpt (K5), the model answers: job J-774 failed with E-ACT-401, a missing activation token, followed by the runbook's five resolution steps. Findings must cite ids that exist in the run, and unknown ids are flagged. The response carries request_id and trace_id, linking the UI's trace screen to Jaeger.

Four walls between tenants

Isolation can't depend on every developer remembering a WHERE clause. Each wall below stops a leak on its own; the lower ones exist for the day the upper ones fail.

ALTER TABLE document_chunks ENABLE ROW LEVEL SECURITY;
ALTER TABLE document_chunks FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON document_chunks
  USING      (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid);

-- the app connects as:
CREATE ROLE tenantpilot_app LOGIN NOSUPERUSER NOBYPASSRLS;

Why NULLIF. Once a pooled connection has used the setting, current_setting() returns '' instead of NULL, and ''::uuid throws. NULLIF turns it into NULL, so a query with no tenant fails closed: zero rows.

Why a second role. Superusers skip RLS and table owners can disable it. The app is neither: it can read and write rows but can't alter tables, and it can append to the audit log but never edit or delete it.

Tested, not assumed. 403 for non-members, 404 for another tenant's run id, zero rows with no tenant set, and an insert for another tenant rejected by WITH CHECK.

services/agent/policy.py · services/mcp_server/auth.py · services/agent/runtime.py

Every tool call passes four gates

The model proposes and code decides. A tool call has to clear four independent checks, and anything that changes a customer's system waits for a person.

gate 1

Offered to the model?

Only tools the tenant enabled are listed. BetaCorp's agent never even sees create_ticket.

gate 2

Allowed this turn?

Permissions are re-read every turn, so revoking a tool stops runs already in flight. Arguments are validated against the JSON Schema.

gate 3

Accepted by MCP?

The service token lists the allowed tools and the server checks it again. A user's JWT is rejected outright: different secret, different audience.

gate 4

Changes a customer system?

readOnlyHint: false means stop: the run saves its transcript and waits in awaiting_approval.

packages/context/builder.py · packages/knowledge/

Context is a budget, not a dump

Acme's config caps the prompt at 6,000 tokens. The ContextBuilder spends that budget on the most useful evidence and writes down why each chunk made the cut, or didn't.

  1. Retrieve up to 12 candidates from the tenant's HNSW index (top-k × 2), filtered by tenant and by RLS.
  2. Drop anything under the relevance floor (vector score 0.02, tuned for this embedder).
  3. Remove exact duplicates and near-duplicates (≥ 0.85 term overlap), keeping the stronger copy.
  4. Rank by 0.6 × vector + 0.3 × lexical overlap + 0.1 × entity match (C-104, E-ACT-401).
  5. Fill the budget highest-value first, and label survivors K1, K2 … for citation.

Every decision is logged. In the C-104 run, K2 was kept as “rank 2: vector=0.10 lexical=0.33”, and three chunks were dropped as “below relevance floor” (scores 0.011, 0.011 and 0.000). The other reasons are “near-duplicate of …” and “over token budget”. The trace screen shows this table for every run.

Tool results get the same treatment: fitted to the reserve, redacted, and labelled T1, T2 … An answer that cites an id that never existed in the run is flagged as unsupported.

packages/connectors/ · packages/schemas/canonical.py

Two customers, one data model

Acme exposes a REST API; BetaCorp granted read-only access to a Postgres CRM. Both answer the same get_customer tool, because each connector carries a declarative field map instead of custom code.

REST connector

Retries 5xx, 429 and timeouts with backoff and stops at 3 attempts. 404 means not found and 401/403 means bad credentials; other 4xx are never retried. Path values are URL-encoded so input can't change the endpoint.

Postgres connector

Named, parameterized, single-statement SELECTs, run in read-only transactions with a statement timeout. The model supplies values; it never supplies SQL.

Credentials

Stored Fernet-encrypted in the tenant's RLS-protected secrets table and referenced as db://<id>. The API hands back the reference, never the key.

packages/core/telemetry.py · services/agent/recorder.py

One trace across the MCP hop

Each agent run is a single OpenTelemetry trace. Ordinary HTTP calls carry a traceparent header; the MCP SDK carries the same context inside the JSON-RPC _meta field, so the MCP server's spans join the trace with no extra code.

Logs

JSON lines carrying request_id, tenant_id, run_id and trace_id. API keys, bearer tokens, JWTs and DSN passwords are scrubbed before a line is written.

Metrics

agent_requests_total, agent_latency_seconds, tool_calls_total, tool_failures_total, retrieval_latency_seconds: labelled by tenant and tool, never by run.

Dashboards

Grafana shows success rate, p95 latency, requests per minute, tool failures, tokens, approval decisions and customer-system outcomes.

.github/workflows/ · helm/tenantpilot/ · infra/terraform/

From commit to cluster

Pull requests run every test against real Postgres and Redis. Merges ship the exact image that was tested: first to a throwaway Kubernetes cluster inside the CI runner, and only then onward.

Probes

Liveness on /api/health; readiness on /api/ready, which checks only Postgres and Redis, so a slow optional dependency never pulls a healthy pod.

Scaling

An HPA scales the API on CPU (2–4 pods on kind), a PodDisruptionBudget keeps one pod up through node drains, and rolling updates never drop below capacity.

Secrets

Runtime secrets and database-owner credentials live in separate Secrets. The owner password reaches only the migration initContainer and the seed Job.

Guardrails

values.schema.json rejects a bad value at helm install instead of letting pods crash-loop after deployment.

Hardening

Non-root containers, a read-only root filesystem, every Linux capability dropped, and no Kubernetes API token mounted.

Infrastructure

Terraform for EKS, RDS, ElastiCache, S3 and ECR, using EKS Pod Identity and an RDS-managed master password, so no static AWS keys or DB passwords sit in code.

What broke, and what it taught

Every one of these happened during the build. Each one makes a better interview answer than a feature list does.

What brokeWhyLesson
Seeding crashed with “expected list or ndarray”pgvector's SQLAlchemy type already turned vectors into text; the asyncpg codec wanted a list.Two layers “helping” with the same conversion collide.
Answers lost their resolution stepsThe relevance floor (0.05) was tuned for semantic scores; the lexical embedder scored the steps chunk at 0.048.Thresholds belong to the embedder. The trace named the dropped chunk.
An eval failed on a policy questionThe planner answered from the top chunk, but the right one was K2.Evals plus traces point at the failing stage: synthesis, not retrieval.
Readiness would have probed MCPA slow optional dependency would fail the probe and pull healthy pods.Readiness means “can serve traffic”; optional parts degrade.
docker compose build: “image already exists”Five services built the same tag in parallel.One artifact, one build.
Worker spans never reached JaegerRQ's forked child exited before the span exporter flushed.Short-lived processes must flush telemetry.
Pods crash-looped on kindenvironment: kind wasn't an allowed setting.Failing at startup is good; failing at helm install is better.
A new image never rolled outThe mutable tag local left the pod spec unchanged.Kubernetes rolls on spec changes; tag images with the commit.
“-f: command not found” mid-deployThe script was edited while bash was still running it.Bash reads a script as it goes.
ingress-nginx was the first pickIt was archived in March 2026.Check that a dependency is still maintained.
Code written from memory didn't match realityMCP SDK v2 renamed FastMCP; Anthropic SDK 1.x dropped temperature; Helm 4 renamed --atomic; Actions were majors ahead.Read the installed source or the registry first.
The Docker demo pointed at localhostThe laptop seed had stored localhost URLs.Seeds should converge to their environment, not just skip.

the two-minute version

The interview version

Problem
Every customer has different systems, data shapes, permissions and production constraints, so one agent can't simply be pointed at them.
Decision
I separated customer configuration from the agent runtime: connectors map each customer into canonical objects, and tools are discovered over MCP.
Risk
Tool access and tenant isolation were the dangers, so I enforced both in code outside the prompt, ending with Postgres Row-Level Security and a database role that can't bypass it.
Production
One image, Helm with probes, autoscaling and network policies, and a pipeline that deploys the exact tested digest and gates releases on evals.
AI
Context is a budgeted pipeline with a reason for every chunk, and every claim must cite a source that exists in the run.
Reliability
Traces and evals make failures reproducible. The trace showed the retriever dropping the resolution-steps chunk at 0.048 against a 0.05 floor.
